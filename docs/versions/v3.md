# Version 3 (V3): Explicit Job Lifecycle & State Management

## V3 Objective
The primary goal of Version 3 is to establish an **explicit, thread-safe job lifecycle and execution state model** that cleanly separates job definitions from runtime execution metadata, enforces valid state transitions, supports scheduled job cancellation, and tracks failure information.

## V2 Limitations Addressed
- **Implicit Execution State**: V2 tracked job execution solely through log statements without maintaining explicit, queryable status objects.
- **No Job Cancellation**: In V2, once a job was registered in the scheduler, there was no mechanism to cancel or prevent it from running.
- **Unrecorded Failures**: When a task threw an exception in V2, the exception was caught and logged, but no runtime failure object or error metadata was retained.

## Job Definition vs. Execution State
- **`Job` (Immutable Definition)**: Java record encapsulating static job attributes (`id`, `name`, `scheduledAt`, `task`).
- **`JobExecution` (Runtime State & Metadata)**: Mutable wrapper representing the lifecycle status (`JobStatus`), timestamps (`startedAt`, `completedAt`), and exception data (`failure`).

## Domain Model & JobStatus
`JobStatus` defines exactly 5 explicit lifecycle states:
- **`SCHEDULED`**: Job is registered in the scheduler queue and awaiting due time.
- **`RUNNING`**: Job has been polled and submitted to worker threads for execution.
- **`COMPLETED`**: Job completed task execution successfully.
- **`FAILED`**: Job execution failed due to an unhandled exception or dispatch error.
- **`CANCELLED`**: Job was cancelled prior to execution start and will never run.

### Terminal States
`COMPLETED`, `FAILED`, and `CANCELLED` are terminal states (`isTerminal() == true`) and cannot transition to any other state.

## Valid State Transitions & State Machine Rules
The lifecycle enforces strict transition rules:
- `SCHEDULED -> RUNNING` (upon scheduler dispatch)
- `SCHEDULED -> CANCELLED` (upon cancellation before execution)
- `RUNNING -> COMPLETED` (upon successful task execution)
- `RUNNING -> FAILED` (upon task exception or submission error)

All other state transitions (such as `COMPLETED -> RUNNING`, `CANCELLED -> RUNNING`, `SCHEDULED -> COMPLETED`, `FAILED -> COMPLETED`) are invalid and rejected with an `IllegalStateException` or `boolean false`.

## Cancellation Semantics
V3 cancellation is defined as **preventing a scheduled job from starting**:
- Only `SCHEDULED -> CANCELLED` is supported.
- Cancellation of `RUNNING` or terminal jobs is strictly rejected (`markCancelled()` returns `false`).
- Forcible termination of running Java threads (`Thread.interrupt()`) is intentionally excluded.
- A cancelled job in the priority queue is skipped by the scheduler and never submitted to `JobExecutor`.

## Execution Metadata & Failure Handling
`JobExecution` captures:
- Target `Job` reference and current `JobStatus`.
- Execution timestamps: `startedAt` (Instant) and `completedAt` (Instant).
- Derived execution `duration` (`Duration.between(startedAt, completedAt)`).
- Exception payload (`failure`) recorded upon transition to `FAILED`.

## Concurrency Considerations & Thread Safety
`JobExecution` state transitions use `synchronized` atomic operations to guarantee thread safety:
- **Race Condition Prevention**: If Thread A attempts `SCHEDULED -> RUNNING` while Thread B attempts `SCHEDULED -> CANCELLED`, exactly one transition succeeds (returns `true`), and the losing operation is rejected.
- **PriorityQueue Ownership**: `JobScheduler` retains single-threaded ownership of the `PriorityQueue<Job>` and manages job lookups via `ConcurrentHashMap`.

## Testing Strategy
The JUnit 5 test suite verifies:
- Initial state initialization (`SCHEDULED`).
- All valid and invalid state transitions.
- Terminal state immutability.
- Scheduled job cancellation and execution prevention.
- Exception capture and failure metadata recording.
- Concurrent transition races between scheduler dispatch and cancellation.
- V1 and V2 regression suites.

## V3 Limitations
- **In-Memory State**: State remains volatile in-memory.
- **Single-Node Execution**: State transitions operate within a single JVM process.

## Explicitly Excluded V4+ Features
- Automatic job retries & exponential backoff policies (deferred to V4)
- Recurring jobs & cron expression parsing
- Persistent storage (PostgreSQL, Redis)
- REST APIs & Web UI interfaces
- Distributed scheduling & multi-node coordination
