# Version 4 (V4): Controlled Failure Recovery & Retry Engine

## V4 Objective
Version 4 introduces **controlled failure recovery** through execution attempt tracking, configurable retry policies, failure classification, exponential backoff delay calculation, and retry lifecycle integration.

## Why Retry Exists
In distributed or multi-component applications, execution failures often occur due to temporary disruptions (e.g., transient network timeouts, lock contention, or rate limits). Rather than immediately marking a job as permanently `FAILED`, V4 enables controlled retries to increase execution reliability without requiring manual intervention or job re-submission.

## Domain Model Evolution: Job vs. JobExecution vs. ExecutionAttempt
- **`Job` (Immutable Definition)**: Static record (`id`, `name`, `scheduledAt`, `task`). The job identity remains **unchanged** across all retries. Retries do **not** create new `Job` objects (e.g., `job-1-retry-1`).
- **`JobExecution` (Runtime Lifecycle)**: Tracks the overall execution lifecycle (`JobStatus`). Retains a history of `ExecutionAttempt` records.
- **`ExecutionAttempt` (Individual Execution Attempt)**: Represents a single execution attempt of a job (`attemptNumber`, `startedAt`, `completedAt`, `outcome`, `failure`).

### Crucial Architectural Distinction: Retry != Recurrence
- **Retry**: Multiple attempts (`ExecutionAttempt`) within the **same** `JobExecution` for the **same** `Job` instance to recover from failure.
- **Recurrence (V6 Future)**: Periodic creation of **separate** `JobExecution` instances over time.

## Retry Policy & `maxAttempts` Semantics
`RetryPolicy` encapsulates retry rules:
- **`maxAttempts`**: Defines the **TOTAL** number of execution attempts allowed (e.g., `maxAttempts = 3` means Attempt 1, Attempt 2, and Attempt 3; NOT initial attempt + 3 retries).
- **Default V3 Behavior**: Existing jobs without explicit policies default to `maxAttempts = 1` (`RetryPolicy.noRetry()`), ensuring backward compatibility without unexpected retries.

## Failure Classification: Transient vs. Permanent
- **`FailureType.TRANSIENT`**: Temporary error eligible for retry (e.g. `NetworkTimeoutException`).
- **`FailureType.PERMANENT`**: Unrecoverable error (e.g. `InvalidDataException`) that fails immediately without retry.
- **`FailureClassifier`**: Evaluates `Throwable failure`. `DefaultFailureClassifier` conservatively treats failures as `PERMANENT` unless explicitly matched against a set of retryable exception types.

## Exponential Backoff Calculation
- **`ExponentialBackoffStrategy`**: Calculates delay before the next attempt:
  $$\text{delay} = \text{initialBackoff} \times 2^{(\text{attemptNumber} - 1)}$$
- **Clamping**: Max delay is clamped to `maxBackoff`.
- **Overflow Safe**: Prevents numerical overflow during duration arithmetic. No jitter in V4.

## Centralized Retry Scheduling vs. Worker Pool Loops
Retries are managed centrally by `JobScheduler` and `PriorityQueue`:
- **Why NOT in worker threads?** Implementing a retry loop (`while (retry) { execute(); }`) inside `JobExecutor` worker threads would block worker threads during backoff delays, waste thread pool capacity, bypass priority queue scheduling order, and prevent job cancellation while waiting.
- **Scheduler-Led Retries**: When a worker thread finishes an attempt with `FAILED`, `JobScheduler` evaluates `RetryPolicy`, calculates backoff, transitions `JobExecution` `FAILED -> SCHEDULED`, and re-enqueues the job into `PriorityQueue` for the calculated future `Instant`.

## Cancellation During Retry Waiting
If a user cancels a job while it is in `SCHEDULED` state waiting for backoff delay:
- `JobExecution` transitions `SCHEDULED -> CANCELLED`.
- When the backoff due time arrives, `JobScheduler` peeks the job and attempts `markRunning()`, which returns `false`.
- The scheduler skips execution and Attempt 2 never runs.

## Future Compatibility (V5 - V9)
V4 is architected to seamlessly integrate with planned future versions:
- **V5 (Workflow / Dependencies)**: Retries complete before dependent downstream jobs are unblocked.
- **V6 (Recurring Jobs)**: Recurrence engines create new `JobExecution` instances, while V4 manages retries per execution.
- **V7 (Persistence)**: Attempt history and status transitions can be persisted atomically to a database.
- **V8 (REST / External Interfaces)**: Status endpoints can expose attempt counts and failure reasons.
- **V9 (Observability)**: Retry counts and backoff metrics can be exported directly from `JobExecution` metadata.
