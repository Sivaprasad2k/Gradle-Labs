# Version 2 (V2): Concurrent Execution Engine

## V2 Objective
The primary goal of Version 2 is to **decouple job scheduling from job execution** and introduce **bounded concurrent execution** using Java's `ExecutorService`.

## V1 Limitations Addressed
- **Sequential Head-of-Line Blocking**: In V1, the scheduler executed tasks synchronously on the main thread. A long-running job prevented all subsequent due jobs from running on schedule.
- **Single-Threaded Execution**: V1 was restricted to single-threaded sequential processing, failing to utilize multi-core hardware.

## Architecture
V2 introduces a dedicated `execution` package to separate concerns cleanly:

```text
com.siva.jobscheduler/
│
├── domain/
│   ├── Job.java
│   └── JobTask.java
│
├── scheduler/
│   └── JobScheduler.java
│
├── execution/
│   └── JobExecutor.java
│
└── JobSchedulerApplication.java
```

## Scheduler vs. Executor Responsibilities

### `JobScheduler` (Scheduler Responsibility)
- Owns the single-threaded `PriorityQueue<Job>`.
- Registers jobs and calculates when the head job is due.
- Waits until the scheduled execution time (`scheduledAt`).
- Polls due jobs from the queue and dispatches them to `JobExecutor`.
- **Does NOT** call `JobTask.execute()` directly.
- Triggers graceful shutdown on `JobExecutor` when the queue becomes empty.

### `JobExecutor` (Execution Responsibility)
- Owns a bounded fixed-size worker pool (`Executors.newFixedThreadPool(workerCount)`).
- Receives dispatched jobs via `submit(Job)`.
- Offloads job execution (`JobTask.execute()`) to background worker threads.
- Captures task logs and exceptions without risking thread pool termination.
- Manages worker pool shutdown and awaits termination of submitted tasks.

## Fixed Worker Pool Concurrency Model
V2 configures a fixed number of worker threads (defaulting to 3 in the application demonstration).
- Tasks submitted beyond the worker count wait in `ExecutorService`'s internal task queue.
- Threads are reused across job executions, avoiding the overhead of creating a new `Thread` per job.
- Unbounded custom thread creation is strictly prohibited.

## Scheduling Order vs. Completion Order
Because tasks execute concurrently across worker threads with variable execution durations:
- **Scheduling/Dispatch Order**: Dictated deterministically by `Job.scheduledAt` via `PriorityQueue`.
- **Completion Order**: Non-deterministic and dependent on individual task duration. A quick job scheduled at the same time as a slow job will complete before the slow job finishes.

## Shutdown Behavior
When all registered jobs have been polled from `PriorityQueue`:
1. `JobScheduler` detects `queue.isEmpty()`.
2. `JobScheduler` invokes `JobExecutor.shutdown()`.
3. `ExecutorService.shutdown()` stops accepting new tasks while allowing already-submitted tasks to continue executing.
4. `JobExecutor` awaits worker thread termination.
5. All worker threads complete, and the application exits cleanly.

## Concurrency Testing Strategy
Tests are written with JUnit 5 and explicitly avoid arbitrary `Thread.sleep()` calls to prevent flaky tests.
- **Synchronization Primitives**: `CountDownLatch`, `AtomicInteger`, and `AtomicBoolean` are used to coordinate thread execution deterministically.
- **Resource Management**: Latches and thread releases are placed inside `try...finally` blocks to ensure executors and worker threads shut down cleanly even when test assertions fail.

## V2 Limitations
- **In-Memory State**: State remains volatile in-memory. Unscheduled/pending jobs are lost if the process is terminated forcibly.
- **No Dynamic Job Registration During Sleep**: The scheduling loop uses `Thread.sleep()` for future jobs on the scheduling thread.

## Explicitly Excluded Future Features
- Persistence (PostgreSQL, Redis)
- Retry logic and exponential backoff
- Recurring jobs and cron expressions
- Job state machines
- Distributed scheduling
- REST API / Web UI / Spring Framework
