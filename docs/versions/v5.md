# Version 5 (V5): Job Dependencies & Workflow Control

## V5 Objective
Version 5 introduces **job dependencies, DAG workflow validation, and scheduler state controls**. It enables jobs to depend on the successful completion of prerequisite jobs before becoming eligible for execution.

## Why Dependencies Were Introduced
Real-world automation workflows often consist of multi-stage processing pipelines where step $N$ requires outputs produced by step $N-1$. V5 provides built-in workflow coordination directly within the scheduler without requiring external orchestrators.

## Domain Model Evolution: Job vs. JobExecution vs. ExecutionAttempt
- **`Job` (Immutable Definition)**: Static record including immutable `Set<String> dependencyIds` and `FailurePolicy failurePolicy`. Dependencies refer strictly to stable Job IDs.
- **`JobExecution` (Runtime State)**: Includes `JobStatus.BLOCKED`. Tracks runtime execution metadata.
- **`ExecutionAttempt` (Attempt History)**: Retains attempt-level outcomes for V4 retries.

### Crucial Architectural Rules
- **Retry != Recurrence**: A retry is another attempt within the same `JobExecution`. Recurrence (V6) will eventually create separate `JobExecution` instances.
- **Dependency != Retry**: Dependencies govern inter-job execution ordering; retries govern intra-job failure recovery.
- **FailurePolicy.CONTINUE Does NOT Override Dependencies**: A `FailurePolicy.CONTINUE` policy on a failed job allows unrelated independent jobs to continue executing, but dependents of the failed job **must remain BLOCKED**.

## Dependency Graph & Cycle Detection
- **`DependencyGraph`**: Represents job dependency relationships by stable Job IDs (`dependencies` and `dependents` maps).
- **DAG Validation**: Graph must be an Acyclic Directed Graph.
  - **Self-Dependency Rejection**: `A -> A` is rejected immediately.
  - **Cycle Detection**: Uses a Depth-First Search (DFS) algorithm (`dfsCycle()`) during job registration. Any cycle (e.g. `A -> B -> C -> A`) throws an `IllegalArgumentException`.
- **Unknown Dependency Validation**: Registration fails if a job declares a dependency ID that is not registered.

## BLOCKED Semantics & PriorityQueue Isolation
- **Initial Status**:
  - Jobs with no dependencies register as `SCHEDULED` and are offered to `PriorityQueue`.
  - Jobs with unsatisfied dependencies register as `BLOCKED` and are **NOT** added to `PriorityQueue`.
- **Why Separate PriorityQueue from DependencyGraph?**:
  - `DependencyGraph` answers: *"Is this job eligible to execute?"*
  - `PriorityQueue` answers: *"Among eligible jobs, which due job should execute next?"*
  - Keeping blocked jobs out of `PriorityQueue` eliminates busy-polling overhead.

## Dependency Completion & Unblocking
When a job reaches `JobStatus.COMPLETED`:
1. `JobScheduler` identifies all direct dependents via `dependencyGraph.getDependents(completedJobId)`.
2. For each dependent in `BLOCKED` status, the scheduler checks if all declared dependencies have status `COMPLETED`.
3. If all dependencies are satisfied, the dependent transitions `BLOCKED -> SCHEDULED` and is offered to `PriorityQueue`.

## Retry / Dependency Interaction
For dependency chain `A -> B`:
- If job A fails attempt 1 transiently and is scheduled for a retry attempt:
  - Job B remains **`BLOCKED`** while job A is retrying.
  - Job B becomes eligible ONLY after job A's overall `JobExecution` reaches `JobStatus.COMPLETED`.
- If job A exhausts retries and stays `FAILED`, job B remains **`BLOCKED`**.

## Failure Policy & Scheduler State

### `FailurePolicy`
- **`CONTINUE`** (Default): Terminal failure of the job does not stop unrelated scheduling. Dependents of the failed job remain `BLOCKED`.
- **`HALT_SCHEDULER`**: Terminal failure of the job transitions `SchedulerState` to `HALTED`.

### `SchedulerState`
- **`RUNNING`**: Normal scheduling operations.
- **`HALTED`**: Suspends new job dispatches and retries. **Active running tasks are allowed to finish cleanly** (not forcibly killed).
- **`STOPPED`**: Scheduler explicitly shut down.

### Resumption (`resume()`)
- `resume()` transitions `HALTED -> RUNNING`.
- Re-evaluates blocked jobs and resumes scheduling.
- **Jobs depending on permanently failed critical jobs remain `BLOCKED`**.

## Cancellation Semantics
- A blocked job can be cancelled: `BLOCKED -> CANCELLED`.
- A cancelled blocked job will **never** be rescheduled or unblocked when its prerequisites later complete.

## Future Compatibility (V6 - V9)
- **V6 (Recurring Jobs)**: Recurrence engines create new `JobExecution` instances; dependency definitions remain stable ID-based.
- **V7 (Persistence)**: ID-based dependency representations are easily reconstructable from storage.
- **V8 (REST / External Interfaces)**: Clean domain methods enable external workflow inspection, halt, and resume.
- **V9 (Observability)**: Graph topology and blocked state durations are directly queryable from `DependencyGraph` and `JobExecution`.
